# Spec — GameMaster v5.2.0

## Identity

- **Name:** GameMaster (`worker_clean`)
- **Label:** AI Game Master — text adventures narrated by Claude, built on SISO
- **Version:** 5.2.0 (`VERSION`)
- **Type:** web application (PHP backend + static frontend); not a platform component (no manifest)
- **Language:** PHP ≥ 8.1 (tested on 8.3), ES-module JavaScript frontend; no Composer or npm dependencies
- **Spec compliance:** SISO Principles — core **2.0** (`doc/SISO-principles.md`) — see `doc/conformance.md`
  (compliant, with two recorded departures, G1 and G2)
- **Core:** SISO core **13.1.0**, vendored unchanged in `siso/` — the PHP instance runs the back end, the
  JavaScript instance runs the client; pinned by `doc/siso-core-13.1.0.sha256`
- **Status:** active
- **Last modified:** 2026-10-20

## Purpose

Players pick a world template and type actions; Claude narrates the result and proposes state changes
(inventory, entities, stats, flags); the game applies the changes it can verify and saves the state.
Worlds: a derelict spaceship, WarGames, the Matrix, and a Portland scavenger hunt with real geography,
game time, money and ten landmarks. Zones can be generated by the AI on demand or ahead of the player.

## Dependencies

- **Runtime:** PHP CLI/FPM with `curl` and `json`. Dev server: `php -S localhost:8080 router.php`.
  The web server must serve `/public/` and `/siso/js/code/` (`.mjs` as `text/javascript`).
- **Tests:** PHP 8.1+ and Node 18+ (Node 22.15+ runs the core's copy-count cases, else they print
  "skipped"). The optional browser check needs Playwright with Chromium.
- **External:** the Anthropic Messages API (key from `../keys.json` or `ANTHROPIC_API_KEY`); without a
  key the mock AI transport answers (`GAMEMASTER_MOCK_AI=true` forces it).
- **Frontend:** a browser with ES modules (Google Fonts, optional).

## Architecture in one paragraph

**Server.** Each HTTP request (or job) becomes **one entry event** entered into a fresh core 13 stream
holding all 37 gates. Gates are pure and routed by event type. A gate that needs something from outside
returns a **request event** that no gate claims — `io_read`, `io_write`, `io_collect`, `ai_call` — so it
settles as **residue**. After each propagation the **Driver** (the boundary) **takes** the residue,
performs each request, and enters the **reply event whose type the request named**, carrying the
request's `carry` plus the result; that reply causes the next gate. The flow ends with an
**`http_response`** event, which the handler sends. The clock and entropy come in as data (`now`,
`nonce` on entry events; `at` on write replies). A gate that throws, loops or returns a non-event
rejects its propagation (core K5); the handler answers 500.

```
HTTP ──▶ handler ──entry──▶ Stream(37 gates) ──take──▶ io_read / io_write / ai_call / io_collect
                                  ▲                                   │
                                  └── entry: reply (type named) ◀── Driver (FileStore, AiTransport)
                           take: http_response ──▶ handler ──▶ HTTP
```

**Client.** The page runs the same model on the core's JavaScript instance. Every user action (page
load, Start, a command, a chip, Retry) becomes one entry event carrying the client **session**
(`{gameId, playerName, busy}`) into a stream holding the 7 client gates (`public/js/gates`). A gate that
needs the server returns `api_call`; one that changes the page returns a render instruction (`ui_*`); one
that changes the session returns `session`. The client driver (`public/js/boundary/driver.mjs`) takes the
residue, fetches (`boundary/http.mjs`) and enters the reply, draws each `ui_*` event (`ui/*.js`), and
keeps the latest session to put on the next entry. A rejected client propagation commits nothing; the
driver then enters `client_rejected`, whose gate frees the page and shows the error overlay.

```
click/Enter ──▶ app.js ──entry (+session)──▶ Stream(7 gates) ──take──▶ api_call ──▶ fetch ./api/…
                                                    ▲                    ui_*     ──▶ ui/*.js (DOM)
                                                    │                    session  ──▶ kept for next entry
                                                    └──── entry: reply {carry, http} ◀── fetch answers
```

## Contracts

### REST API (unchanged for the frontend)

| Method | Path | Entry event | Success | Rejections |
|---|---|---|---|---|
| GET | `/api/templates` | `templates_requested` | 200 `{success, data:[{id,name,theme,description}]}` | — |
| POST | `/api/game/new` `{worldTemplateId?, playerName?, gameId?, overwrite?}` | `game_create_requested` | 201 `{success, message, data:{gameId, worldTemplateId, narrative, currentZone, turnCount:0, player, suggestedActions}}` | 422 validation, 400 bad template / save failed, 409 exists |
| GET | `/api/game/{gameId}[?full=true]` | `game_load_requested` | 200 `{success, data:{gameId, narrative, currentZone, turnCount, player, suggestedActions[, gameState]}}` | 400 bad id, 404 missing/unreadable/corrupt |
| POST | `/api/game/{gameId}/action` `{action}` | `action_submitted` | 200 `{success, data:{narrative, suggestedActions, player, turnCount, currentZone, lastSaved}, error:null, meta:{tokensUsed, turnTokens}}` | 422 validation or in-world failure (same body shape, `success:false`), 400 bad id |
| POST | `/api/action` `{gameId, action}` | `action_submitted` | as above | as above |
| POST | `/api/game/{gameId}/zone/generate` `{zoneId, parentZoneId?, direction?, constraints?}` | `zone_generate_requested` | 201 `{success, message, data: zone}` | 400, 422, 404 game, 409 exists, 500 failed |
| POST | `/api/game/{gameId}/zone/pregenerate` `{fromZoneId}` | `zone_pregenerate_requested` | 200 `{success, message, data:{fromZoneId, requested, generated:[{zoneId,name}], errors:[{zoneId,error}]}}` | 400, 422, 404 |
| GET | `/api/game/{gameId}/zone/{zoneId}` | `zone_get_requested` | 200 `{success, message, data: zone}` | 400, 404 |
| GET | `/api/game/{gameId}/zones` | `zone_list_requested` | 200 `{success, message, data:{gameId, count, zones}}` | 400 |
| DELETE | `/api/game/{gameId}/zone/{zoneId}` | `zone_delete_requested` | 200 `{success, message, data:{deleted}}` | 400, 404, 500 |
| GET | `/api/health` | — (probes in api.php) | 200/503 | — |

Validation errors are `{success:false, error:"Validation failed", errors:{field: message}}`; other errors
`{success:false, error}`.

### Boundary request events (`src/Events/Io.php`)

| Request | Data | Reply data (carry + …) |
|---|---|---|
| `io_read` | `{reads:{name: spec}, reply, carry}` | `reads:{name:{status, data}}`, status ∈ ok, missing, corrupt, unreadable, invalid |
| `io_write` | `{writes:{name: spec+op}, reply, carry}` (op put with content, or delete) | `writes:{name:{ok}}`, `at` |
| `io_collect` | `{types, where, key, expect, reads, reply, carry}` — ready when the driver has taken, for each value in `expect`, an event of `types` matching `where` with `data[key]` = value | `collected:[{type,data}]`, `reads` |
| `ai_call` | `{system, user, reply, carry}` | `ai:{ok, content, usage:{input,output}, model, error:{code,message}\|null}` |
| `http_response` | `{status, body}` | terminal |

Requests settle as residue and are taken by the Driver after every propagation.

Resource specs: `save{gameId}`, `template{templateId}`, `templates{}`, `zone{gameId, zoneId}`,
`zone_index{gameId}`. Ids must match `^[A-Za-z0-9_-]{1,100}\z`; zone id `_index` is reserved.

### Saved game state (`saves/game-{id}.json`)

`gameId, worldTemplateId, created, lastUpdated, turnCount, currentZone, zoneDescription,
player{name, inventory, stats}, entities[{id,name,present,properties}], worldState{day, time,
globalFlags, …}, profile{actionHistory[{turn,action[,time,location]}], observations, patterns},
worldTemplate{theme,tone,worldRules}, budget{sessionTokens, sessionCost, lastTurnTokens}, zones{id:
{name, description, exits, visited, generated}}`; Portland adds `location{name,lat,lng,streetview}`,
`worldState.date`, `worldState.landmarks_visited`, `player.stats.money/landmarks_found`.

### Client boundary events (`public/js/events/io.mjs`)

| Event | Data | Done by |
|---|---|---|
| `api_call` | `{method, path, body, reply, carry}` (path relative to `./api`) | `boundary/http.mjs`; reply = carry + `http:{status, contentType, json, error}` (status 0 when no reply) |
| `session` | `{gameId, playerName, busy}` | the driver keeps it; entry events carry it back |
| `ui_worlds` | `{options:[{id,name}]}` | `ui/screens.js` — the world picker |
| `ui_start_button` | `{busy}` | `ui/screens.js` |
| `ui_screen` | `{screen:'game'}` | `ui/screens.js` — switch, glitch, focus; then `ui/output.js` re-measures the log |
| `ui_busy` | `{busy, clearInput}` | `ui/screens.js` (input) + `ui/overlays.js` (spinner) |
| `ui_hud` | `{zone, turn, player, chips}` (null: leave as is) | `ui/stats.js` |
| `ui_status` | `{text, kind}` | `ui/stats.js` |
| `ui_log` | `{kind: narrative\|command\|error, text, inventory}` | `ui/output.js` |
| `ui_error_overlay` | `{visible, endpoint, code, message}` | `ui/overlays.js` |

Client entry events (built in `app.js`): `app_started {}`; `start_submitted {playerName, worldTemplateId,
gameId, session}`; `command_entered {action, session}`; and, from the driver, `client_rejected {code,
message, entryType, session}`. Render instructions from one propagation are drawn in whatever order the
residue gives (a multiset), so none may depend on another: at most one `ui_log` per propagation, and
`ui_screen` re-measures the log. Every field a client gate shows goes through `pure/text.mjs` `text()`,
which never throws on hostile JSON.

## Gates

All gates are pure (P). Flows (⇒ crosses the boundary):

- **Templates:** `templates_requested` → io_read ⇒ `templates_loaded` → 200
- **New game:** `game_create_requested` → io_read{template, existing} ⇒ `game_create_loaded` →
  `game_template_ready` → io_write{save} ⇒ `game_created` → 201
- **Load:** `game_load_requested` → io_read ⇒ `game_load_read` → 200
- **Turn:** `action_submitted` → io_read{save} ⇒ `turn_state_loaded` (classify) → io_read{template} ⇒
  `turn_template_loaded` | `portland_turn_loaded` → ai_call ⇒ `turn_ai_replied` → io_read{save} ⇒
  `turn_apply_loaded` (classify) → `generic_turn_parsed` | io_read{template} ⇒ `portland_turn_parsed` →
  `turn_applied` → `turn_accounted` → io_write{save} ⇒ `turn_saved` → 200; failures → `turn_failed` → 422
- **Zones:** `zone_generate_requested` → io_read ⇒ `zone_generate_loaded` →
  [`zone_target`, io_collect]; `zone_pregenerate_requested` → io_read ⇒ `zone_pregenerate_loaded` →
  [`zone_target` ×N, io_collect]; `zone_target` → ai_call ⇒ `zone_ai_replied` → `zone_parsed` |
  `zone_failed` (residue); io_collect ⇒ `zones_settled` → io_write ⇒ `zone_generate_stored` (201/500) |
  `zone_pregenerate_stored` (200)
- **Zone get/list/delete:** `zone_get_requested` → ⇒ `zone_get_read`; `zone_list_requested` → ⇒
  `zone_list_read`; `zone_delete_requested` → ⇒ `zone_delete_loaded` → io_write{zone delete} ⇒
  `zone_file_deleted` → io_write{index} ⇒ `zone_deleted` → 200

**Per-gate tests run through the real core.** Both helpers (`sisoTests/helper.php`,
`sisoTests/client/helper.mjs`) register the gate under test alone on a fresh core 13 stream, enter one
event of its signature and take the residue, so the core judges what the gate returned (a throw, a
self-loop or a non-event return fails the case). Each census lists the registered gates from the code,
checks every gate module on disk is registered, checks each test obtains its gate via
`gate('<signature>')`, runs each file in its own process, and checks accepted cases share one output
shape (server: event types, reply types, written resources, HTTP status; client: event types, and for
`api_call` its method, path pattern and reply). `rejected …` cases are excluded; on the server
`accepted (class X)` is compared per class and `accepted (empty fan-out)` may be a subset.

**Chain tests.** `tests/scenarios.test.php` runs handlers → driver → gates → temp files with a scripted
mock AI. `tests/client-scenarios.test.mjs` runs the client gates and driver with a scripted server in
place of fetch and a recorder in place of the DOM. `tests/browser.e2e.mjs` starts the dev server with the
mock AI and plays in headless Chromium (worlds load, start, a typed command, a chip, no console errors).
None of these counts as a gate's test.

Test conventions: no PHPUnit, no `assert()`, no npm packages; `tests/runner.php` turns PHP warnings into
failures (as `api.php` does in production); the JS suites report through the core's harness
(`siso/js/code/harness.mjs`). Prompt tests compare against fixtures produced by the pre-port gates
(`sisoTests/fixtures/README.md`). Budget expectations use Anthropic's published prices.

## Known issues

**Moderate**
- **G1 — server gates throw on a save file with the wrong field types** (valid JSON, e.g. `"player": "x"`,
  `"entities": 5`, `"currentZone": [...]`, `"turnCount": "many"`): TurnRouteGate, ContextBuildGate,
  PortlandContextGate, StateUpdateGate, GameStateGate, ZoneContextGate and ZoneStoreGate can raise a PHP
  type error, or a notice that the production error handler turns into one. Core 13 rejects the
  propagation (SISO_GATE_THREW, nothing committed) and the client gets a 500, as under 5.1.
- **G2 — one AI reply can break a save**: a `statChanges` key such as `globalFlags` overwrites the game's
  own `worldState` field; the turn saves, and every later flag-setting turn answers 500. Present in 5.1.
- Principles 2.0 forbid a gate to throw: G1 and G2 are recorded departures in `doc/conformance.md`, each
  with its fix and a probe in `tests/probes/`. Next phase.
- Budget limits are not enforced (totals only). Automatic pre-generation after a turn is not wired.
- Pre-generation treats template zones (not in the zone index) as ungenerated.
- Boundary logic outside gates: HTTP router/middleware/health roll-up (B1, B2), job queue state
  transitions and retry scheduling (B3) — see `doc/conformance.md`.

**Minor**
- Portland worlds have no inventory guard. Concurrent requests on one game: last write wins.
- Numeric-looking ids in id-keyed maps are encoded as JSON lists.
- Reloading the page loses the client session (the save is on disk; there is no resume).
- A failed game start writes its error into the game screen's log, which is still hidden (as before).
- The dev router serves every file under the project root, `saves/` included (dev server only).
- Tabs in actions are removed rather than collapsed; name `<>` becomes empty; `zones/_queue` vs game id
  `_queue`; `keys.json` is resolved against the working directory.

**Resolved this phase** — see `doc/changelogs/changelog-v5.2.0.md`.
